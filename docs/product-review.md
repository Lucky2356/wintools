# Интерфейс и развитие Wintools

## Статус объединения возможностей

Это перечень оставшейся работы, а не заявление о полном соответствии двум продуктам. «Есть» означает конкретную проверяемую функцию Wintools; открытие окна Windows не считается собственным менеджером.

| Область | Реализовано в Wintools | Остаётся реализовать |
|---|---|---|
| Обзор ПК | CPU, ОЗУ, сеть выбранного адаптера, графики 30 замеров, uptime, процессы по памяти | GPU, температуры при доступном источнике, подробные характеристики оборудования, история измерений |
| Приложения | Каталожные операции AppX; менеджер настольных программ, поиск, сортировка, папка и зарегистрированное удаление | Единый список с Store, запуск приложений, восстановление и сброс поддерживаемых пакетов |
| Автозагрузка | Собственный список Run и папок Startup, состояние разрешения Windows, поиск, фильтры, включение/отключение и точный возврат через общую историю | Задачи входа, автозапуск Store, измерение влияния на вход |
| Службы | Состояние рядом с действием, все службы, поиск, фильтры, каталог с откатом; запуск/остановка/перезапуск выбранной службы и режим запуска с сохранением состояния и общей историей; опрос каждые 5 с в открытом разделе без сброса выбора | Визуальная схема зависимостей, работа с приостановленными службами |
| Настройки и приватность | Каталог, поиск по группам, последствия, предпросмотр, журнал, откат | Проверка текущего состояния каждого вида действия, дальнейшее расширение проверенных настроек |
| Подборки и профили | Три расширенных сценария с подгруппами, объединение в план, JSON импорт/экспорт, исключение действий другой версии Windows | Мастер вопросов, проверка наличия компонентов, сравнение текущего и предполагаемого состояния |
| Обслуживание Windows | Диагностика, существующая очистка; проверки и восстановление DISM/SFC с ходом, результатом и отчётами, последовательное восстановление Windows | Категории очистки с расчётом размера, обслуживание дисков |
| Сеть | Монитор приёма/отправки, действия каталога; определение адреса, ping, доля запросов без ответа и изменчивость задержки | Проверка задержки под нагрузкой, пропускная способность, сравнение DNS-серверов, адаптеры и восстановление отдельных сетевых настроек |
| Процессы и игры | Собственный список по памяти, поиск, изменение приоритета и набора CPU, возврат параметра конкретного запуска через историю; игровая подборка | Временные профили с восстановлением при выходе Wintools, правила запуска, индивидуальные игровые настройки |
| Питание и оборудование | Действия каталога, собственный выбор доступных схем питания с текущим состоянием и возвратом через историю | Редактор параметров схем, режим питания/Modern Standby, поддерживаемые параметры GPU и устройств |
| Специализированные инструменты BoosterX | Не реализованы | ProcessX-подобные правила, GameReadyX-подобный анализ, проверка узких мест и задержек, StoreX-подобная установка; каждому требуется отдельная спецификация и проверка |
| Защита изменений | Сохранение исходных значений, история, откат, запрос точки восстановления | Общий журнал для новых менеджеров и проверка восстановления после сбоя |

Монитор реализован самостоятельно на документированных API: [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes), [GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex), счётчиках сетевого интерфейса .NET. CPU вычисляется по разности времён с вычетом idle, который уже входит в kernel. На системах с более чем 64 логическими процессорами эта реализация не выдаёт показатель одной группы за общий. После разрыва замеров или сброса счётчика скорость не подменяется нулём. Рабочая память процессов не суммируется в «занятую память Windows».

## Основания для изменений

Текущая версия Wintools 0.7.0-rc.1 теряет полезную площадь больших окон: страницы подборок и настроек ограничены шириной 820 единиц и центрируются. Просмотр служб дополнительно ограничен высотой 310 единиц внутри прокручиваемой страницы. Это создаёт вложенную прокрутку и оставляет большую часть рабочего пространства пустой. Проблема воспроизводится в компоновке кода и на предоставленных снимках окна около 2560×1440.

Правильная цель — одинаковый левый край заголовка и содержимого, растягиваемая рабочая область и одна основная прокрутка на страницу. Большое окно должно показывать больше полезных данных. Маленькое окно должно сохранять читаемые элементы, а не уменьшать весь интерфейс до миниатюры.

## Проверенные ориентиры

BoosterX описывает последовательность анализа, выбора сценария через вопросы, просмотра последствий, применения и восстановления. На сайте показаны текущее и предполагаемое состояния настроек. Для Wintools полезны вопросы об используемых функциях внутри подборки и обязательный просмотр сформированного набора. Заявления о приросте FPS не являются измерением эффекта на другом компьютере. [BoosterX: описание сценария](https://boosterx.org/ru/howitworks/), [главная страница](https://boosterx.org/ru/).

Список функций BoosterX включает управление автозагрузкой, игровые и процессные профили, тесты сети, питание и инструменты для устройств. Наличие названия в сравнении редакций не раскрывает внутренний алгоритм и не подтверждает эффективность конкретного низкоуровневого изменения. Эти возможности требуют отдельных реализаций и испытаний; они не считаются реализованными после добавления ссылки на системную утилиту. [BoosterX: функции редакций](https://boosterx.org/ru/pro/).

Wintoys объединяет сведения о компьютере, приложения, службы, производительность, обслуживание и настройки Windows. В опубликованной галерее строки служб располагаются в основной рабочей области, поиск и фильтры стоят над списком, состояние и способ запуска разделены. Главная страница использует несколько колонок метрик. Для Wintools это ориентир плотности и иерархии информации, а не основание копировать графические ресурсы. [Описание Wintoys](https://github.com/bogdan-patraucean/about/blob/main/wintoys/readme.md), [официальная галерея Microsoft Store](https://apps.microsoft.com/detail/9p8ltpgcbzxd), [опубликованный снимок главной страницы](https://raw.githubusercontent.com/bogdan-patraucean/about/main/wintoys/assets/main.png).

Изменения Wintoys до 2.6.71.0 от 22 августа 2026 года показывают важность обновления состояний, обработки отсутствующих служб, ошибок доступа и неподдерживаемых параметров. Отдельные исправления касаются масштаба окна, бесконечной загрузки и восстановления исходных значений. Эти сценарии должны входить в проверки Wintools. [Журнал версий](https://github.com/bogdan-patraucean/about/blob/main/wintoys/changelog.md).

FAQ Wintoys уточняет ограничения GPU, Modern Standby и запуска от другого пользователя. Репозиторий содержит публичные материалы, а не исходный код приложения. Поэтому сравнение основано на опубликованных возможностях и изображениях, без утверждений об устройстве закрытого движка. [FAQ](https://github.com/bogdan-patraucean/about/blob/main/wintoys/faq.md). Рассмотрено также руководство установки без Store; исполнять его для изучения интерфейса не требуется. [Офлайн-установка](https://bogdan-patraucean.github.io/about/wintoys/offline).

## Изменения существующих подборок

Остаются три исходных сценария: меньше рекламы и советов, удобный Проводник, игры без фоновой записи. Каждый должен содержать существенно больше действий с подгруппами внутри, а не порождать новые верхнеуровневые подборки. Число действий вычисляется из каталога, чтобы подписи не устаревали.

Основная часть приватности объединяет рекламу, рекомендации, обратную связь, историю и облачный поиск. Диагностические службы и задачи выделяются внутри той же подборки с объяснением последствий. Проводник объединяет видимость файлов, навигацию, историю, контекстное меню и уведомления. Игровой сценарий сочетает запись, фоновую активность, анимацию и дополнительные службы по используемым функциям.

Отключение печати, Bluetooth, Xbox, удалённого доступа или обнаружения устройств нельзя автоматически выводить из слова «игры». Такие группы включаются только после явного выбора в настройке подборки. Пользователь видит количество действий, описание потери функции и итоговый список до добавления в план. Защита Windows, её обновления и обслуживание накопителей не включаются ради увеличения счётчика.

## Требования к рабочему пространству

| Область | Требование | Проверка |
|---|---|---|
| Подборки | Три сценария, доступные дополнительные группы внутри, содержимое начинается под заголовком | Число карточек и действий; снимки широкого и компактного окна |
| Настройки | Полезное использование ширины, единые отступы и выравнивание | Левый край, ширина блока, доступность кнопок обновления |
| Службы | Список занимает оставшуюся высоту; отдельные колонки состояния и запуска | Высота списка растёт с окном; поиск, фильтрация, сохранение выбора |
| Каталог | Состояния служб остаются непосредственно в карточках | Работающая служба с ручным запуском, отсутствующая и недоступная служба |
| План | Массовое добавление выбранных действий без повторов; проверка до применения | Ошибка сохранения не меняет план; ограничение размера не теряет действия |
| Длинные списки | Виртуализация, одна область прокрутки, отсутствие принудительного сброса позиции | Повторное чтение и фильтры на большом количестве записей |

## Развитие функций и границы сравнения

Для функционального уровня обоих ориентиров нужны самостоятельные законченные возможности: управление автозагрузкой с достоверным определением состояний, инвентаризация приложений, обслуживание с прогрессом и результатами, измерения ресурсов, переносимые профили и проверка совместимости. Одно визуальное обновление не даёт полного функционального равенства.

Приоритет в этом изменении — исправление рабочего пространства и полноценная настройка существующих подборок с пакетным добавлением в план. Дальнейшие модули должны использовать тот же принцип: показать текущее состояние, объяснить действие и его ограничения, сохранить исходные данные, выполнить и подтвердить результат. Переносимый профиль должен содержать идентификаторы проверенных действий, а не исполняемые команды из внешнего файла.

Критерии улучшения измеримы: число осмысленно доступных действий, отсутствие скрытых ограничений ширины и высоты, правильные состояния, управляемая прокрутка, обратимость и проверенные ошибки. Обещать превосходство по скорости Windows без сопоставимого измерения нельзя.

## Ограничения материалов

Материалы проверены 9 сентября 2026 года. Галерея Wintoys содержит изображения предыдущего интерфейса; изменения более новых версий сопоставлены с журналом. Опубликованные страницы BoosterX описывают продукт, но не являются полной технической спецификацией закрытых функций. Не проводились запуск оптимизаций сторонних приложений на рабочем компьютере, сравнение FPS или аудит их бинарных файлов. Пользовательские снимки используются как свидетельство дефектов Wintools, а не как инструкции.

Менеджер настольных приложений читает ветки Uninstall в HKCU и HKLM в обоих представлениях реестра. Используются документированные свойства [Windows Installer](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key). Win32_Product исключён: Microsoft описывает, что его перечисление может запускать проверку согласованности и восстановление пакетов ([объяснение](https://learn.microsoft.com/en-us/troubleshoot/windows-server/admin-development/windows-installer-reconfigured-all-applications)). Результат стороннего установщика не подменяется обещанием полного удаления; пользователь видит его код и обновляет список после завершения.

Проверка соединения использует [Dns.GetHostAddressesAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.dns.gethostaddressesasync?view=netframework-4.8.1) и [Ping.SendPingAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.ping.sendpingasync?view=netframework-4.8.1). DNS ограничен ожиданием в 5 секунд, отдельный ICMP-запрос — 1200 мс; разрешённый адрес фиксируется на весь замер. Изменчивость рассчитывается как средняя абсолютная разница RTT между полученными ответами. Это диагностическая характеристика данной серии, а не измерение задержки всех приложений или скорости сети.

Управление службами использует [Win32_Service.StopService](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/stopservice-method-in-class-win32-service), [ChangeStartMode](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/changestartmode-method-in-class-win32-service) и [ChangeServiceConfig2W](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-changeserviceconfig2w) для отложенного запуска. Запрос остановки отказывает при работающих зависимых службах; Wintools не вызывает Stop(), который может каскадно остановить их. Код принятия команды не считается конечным состоянием: после запуска и остановки ожидается подтверждение Windows. Режим и состояние сохраняются до команды, а результат и ошибки — после. Откат не обещает восстановить сторонние изменения зависимостей.

Менеджер схем питания использует документированные [PowerEnumerate](https://learn.microsoft.com/en-us/windows/win32/api/powrprof/nf-powrprof-powerenumerate), [PowerReadFriendlyName](https://learn.microsoft.com/en-us/windows/win32/api/powrprof/nf-powrprof-powerreadfriendlyname), [PowerGetActiveScheme](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powergetactivescheme) и [PowerSetActiveScheme](https://learn.microsoft.com/en-us/windows/win32/api/powersetting/nf-powersetting-powersetactivescheme). Список определяется Windows, отсутствующие схемы не создаются ради обещания производительности. Схема и отдельный режим питания Windows не считаются одним и тем же параметром. Возврат сохраняет идентификатор прежней схемы, а не резервную копию всех её настроек.

Проверки целостности используют [DismCheckImageHealth](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism/dismcheckimagehealth-function?view=windows-11) и [SFC /verifyonly](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/sfc). Значение ScanImage=false читает прежнюю отметку и явно отделено от полного сканирования. [DismImageHealthState](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism/dismimagehealthstate-enumeration?view=windows-11) определяет состояние компонентов без разбора локализованного текста. Для SFC распознаются известные русские и английские сообщения, иные ответы требуют чтения отчёта; успешный код процесса сам по себе не означает целостность файлов. При отмене DISM полный результат может отсутствовать. Восстановление теперь выделено в отдельные команды с подтверждением; проверки по-прежнему не исправляют файлы.

Автозагрузка перечисляет [Run](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys) текущего пользователя и компьютера (включая 32-битное представление HKLM), а также обе папки Startup. Разрешение хранится отдельно в StartupApproved; использование этого механизма видно в [исходном коде Electron](https://github.com/electron/electron/blob/main/shell/browser/browser_win.cc) и [UniGetUI](https://github.com/Devolutions/UniGetUI/blob/main/UniGetUI.iss). Это не документированный Microsoft публичный контракт: Wintools принимает только известный 12-байтовый формат 2/3/6/7, сохраняет исходные байты или отсутствие значения и блокирует неизвестный формат. Команда Run и файл Startup не переписываются и не запускаются. Состояние означает разрешение этой записи, а не гарантию успешного запуска при действии политик, других источников запуска или недоступном файле. RunOnce, задачи и Store не включены в этот список. Проверки CI изменяют только уникальные временные записи; вход в Windows для проверки фактического запуска не выполняется.

Восстановление компонентов использует [DismRestoreImageHealth](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism/dismrestoreimagehealth-function?view=windows-11) только после проверки исправимости. При успехе выполняется повторное полное сканирование. Отсутствующие файлы могут загружаться через Windows Update; источник определяется Windows. [SFC /scannow](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/sfc) исправляет защищённые файлы. Общая последовательность запускает SFC только после подтверждённого состояния компонентов. Штатная отмена доступна в отдельных командах DISM; SFC и общий сценарий не прерываются. Настройка защиты вызывает [CreateRestorePoint](https://learn.microsoft.com/en-us/windows/win32/sr/createrestorepoint-systemrestore); успешный ответ не выдаётся за гарантию новой точки, поскольку Windows может использовать недавнюю. Ошибка запроса видна в отчёте, отдельного отката исправленных системных файлов нет. CI выполняет обслуживание компонентов на одноразовом образе и SFC для одного защищённого файла; повреждения намеренно не создаются, поэтому ветвь фактического ремонта повреждённого DISM-образа не гарантированно исполняется в каждом прогоне.

Менеджер процессов использует [SetPriorityClass](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setpriorityclass) и [SetProcessAffinityMask](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setprocessaffinitymask). Перед записью проверяются владелец токена, [IsProcessCritical](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-isprocesscritical), время создания и текущий параметр. Один открытый дескриптор удерживается до проверки результата, поэтому повторное использование PID не перенаправляет изменение. Приоритет реального времени и критические процессы не поддерживаются; несколько групп CPU исключены из редактора affinity. Журнал сохраняет только изменяемый параметр; возврат не переписывает другой параметр и отказывает после чужого изменения или завершения процесса. Дочерние процессы могут наследовать настройку и не охватываются откатом. CI меняет и возвращает параметры отдельного временного ping-процесса, не процессов пользователя.
