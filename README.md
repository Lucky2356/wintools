# wintweaks — твики Windows с журналом и откатом

Мини-приложение с одним CMD-интерфейсом: применяет консервативный набор системных
настроек (приватность/телеметрия, UI/Explorer, службы, задачи планировщика,
питание, сеть), умеет чистить диск и восстанавливать сохранённые настройки
через тот же интерфейс.

Перед изменением сохраняется исходное состояние. Очистка диска, удаление Edge
и provisioned-копии AppX имеют ограничения отката, описанные ниже.

---

## Графический portable-интерфейс

Интерфейс использует встроенный WPF: согласованные светлая и тёмная темы, оформленные поля,
переключатели, списки и прокрутка. Сторонние UI-библиотеки не требуются.

**Обновления закрытого репозитория:** в «Настройки → Доступ к GitHub» сохраните fine-grained токен
для `Lucky2356/wintools` с разрешением **Contents: Read-only**. Вход в GitHub в браузере не передаёт
авторизацию приложению. Токен шифруется Windows DPAPI для текущего пользователя; он не попадает в логи.
Не отправляйте токен в переписке. Кнопка «Удалить» удаляет сохранённый доступ.
Проверка релизов и скачивание приватного EXE используют GitHub API с авторизацией.
Если репозиторий публичный, токен не нужен. RC.2 и более старые EXE не умеют авторизоваться:
первое обновление до 0.5.0-rc.1 из закрытого репозитория скачайте вручную, сохранив папку `WintoolsData`.

История группируется по запускам; полностью отменённые записи недоступны для повторного отката.
Если UAC запущен под другим пользователем, операция отменяется до изменения его настроек.

Скачайте **WintoolsPortable.exe** из [GitHub Releases](https://github.com/Lucky2356/wintools/releases/tag/v0.5.0-rc.1)
и положите в отдельную папку с правом записи. Установка не нужна: интерфейс и движок находятся в одном EXE.
Требуется Windows 10 1809+ / Windows 11 **x64** со встроенным .NET Framework 4.7.2 или новее.

- Каталог на русском, поиск по названию/описанию/ID, категории и избранное.
- Светлая, тёмная и системная темы; выбор сохраняется. Каталог, история и настройки доступны в боковом меню.
- Описание и кнопки выбранного действия находятся в отдельной карточке; вывод операций можно свернуть.
- Высокий риск скрыт по умолчанию. Действия применяются по одному после подтверждения.
- Предпросмотр запускает настоящий движок с `/dry`. Вывод отображается в окне.
- История изменений позволяет откатить выбранный запуск; доступны диагностика, verify, папки логов и отчётов.
- Перед системными операциями запрашивается UAC. Сам интерфейс и диагностика запускаются без администратора.
- Глубокое удаление AppX из GUI не предлагается; обычное удаление сохраняет действующие ограничения отката.

Рядом с EXE создаётся `WintoolsData`: движок, настройки, избранное, журнал, резервные копии, логи и отчёты.
Фоновые службы и задания не устанавливаются. Не размещайте программу в каталоге, доступном на запись другим пользователям,
или в пути через junction/symlink. CMD-движок не поддерживает в этом пути символы `! % & " ^ < > |`.

**Обновление:** при запуске приложение проверяет GitHub Releases. Можно отключить проверку или выбрать канал RC.
Кнопка «Обновить и перезапустить» загружает официальный EXE, сверяет размер и SHA-256 из метаданных GitHub,
ждёт закрытия программы и атомарно заменяет файл. Во время работы движка обновление блокируется.
Настройки, журнал и резервные копии сохраняются. Прежний EXE остаётся рядом с расширением `.previous`;
для возврата закройте программу и верните этому файлу имя EXE. При ошибке смотрите `WintoolsData\update-error.txt`.
Скачанные служебные файлы остаются в `WintoolsData\updates`; их можно удалить после закрытия всех экземпляров.
Проверка версии и загрузка отправляют запросы только для обновления, не загружают ваши отчёты или журналы.
Без сети функции обслуживания продолжают работать. SHA-256 не заменяет подпись издателя; EXE пока не подписан.

У portable-версии отдельный журнал. Если изменения ранее выполнялись CLI из другой папки, откатывайте их там:
старые записи могут содержать абсолютные пути к резервным копиям. Не объединяйте журналы вручную.
При переносе между папками сохраняйте весь `WintoolsData`, но учитывайте абсолютные пути уже созданных резервных копий.
Перенос журнала между разными ПК не поддерживается.

Сборка EXE выполняется в GitHub Actions штатным C#-компилятором Windows без NuGet-зависимостей.
CI проверяет запуск интерфейса, делает его снимок, проверяет portable-диагностику, выбор версии обновления,
отказ при неверном SHA-256, блокировку во время работы движка и сохранение предыдущего EXE при замене.

## Рабочий порядок и статус выпуска

Текущая версия: **0.5.0-rc.1**. Это кандидат на выпуск для контролируемого использования.
Проверки GitHub на Windows Server не подтверждают полный цикл клиентской Windows после перезагрузки.

1. Выполните `wintweaks.cmd diagnose` (администратор не нужен). Отчёт в `reports\diagnostic_*.json`
   содержит память, загрузку CPU, свободное место, десять процессов по памяти и записи автозапуска.
   Это моментальный снимок, а не бенчмарк; неполные данные отмечаются отдельно, код выхода — 4.
2. Выберите конкретную проблему и просмотрите действие в меню или через `/dry /id:...`.
3. Примените одно изменение, повторите тот же рабочий сценарий и выполните `verify`.
   Если результат не устраивает — `revert /id:...` или `revert /run:...`.

Приватность, оформление и удаление приложений не гарантируют роста FPS или ускорения ПК.
Проверка автозапуска и свободного места соответствует [рекомендациям Microsoft по производительности](https://support.microsoft.com/en-us/windows/experience/performance-optimization/tips-to-improve-pc-performance-in-windows).
Пороговые подсказки отчёта (10% диска, 15% свободной памяти) — ориентиры инструмента, не диагноз.
В отчёт не включаются команды автозапуска и имена пользователей; названия программ могут раскрывать состав ПО.
Отчёты никуда автоматически не отправляются. Пункт **Q** открывает диагностику из меню.

**Изменения поведения в 0.3:**

- `apply` использует профиль `core` по умолчанию. `balanced` и `extended` выбираются явно.
- `system-change` требует `/id:SYS-...`: общего пресета питания и сети больше нет.
- `cleanup` без ID очищает только временные файлы пользователя и Windows старше трёх дней.
  Дампы, кэши обновлений, DISM, Disk Cleanup и корзина выбираются отдельно.
- Массовое применение в категориях служб, приложений, системы, очистки, Edge и производительности
  отключено: выбирайте действия по карточкам. Массовое применение остальных категорий не включает высокий риск.
- Неизвестный ID, ID другой команды и неизвестный RUNID отклоняются до изменений.
- Очистка не переходит по junction/symlink. Недоступные и занятые файлы учитываются как неполная очистка
  с кодом 4. Пустые каталоги сохраняются. В логе — число файлов, байты и ошибки.
- Очистка кэша обновлений прекращается при ошибке остановки службы; ранее работавшие службы
  запускаются в `finally`, ранее остановленные остаются остановленными.
- Disk Cleanup сохраняет и восстанавливает прежние значения `StateFlags0064`; ошибки подготовки
  запрещают запуск. Экспорт `volumecaches.reg` остаётся страховочной копией на случай аварии процесса.

После успешных проверок обеих платформ GitHub собирает ZIP и SHA-256 из файлов проекта.
Артефакт `release-package` не содержит журналы, резервные копии или отчёты пользователя.
SHA-256 подтверждает целостность скачивания, но не является цифровой подписью издателя.
Не удаляйте старые `state` и `backups` при обновлении: они необходимы для отката.

## Быстрый старт

Запускать **из консоли с правами администратора** (без прав — выход с кодом 2).

```bash
menu.cmd
```

Или обычным CLI:

```bash
wintweaks.cmd help
```

> Распаковывайте проект в доверенный каталог, недоступный для записи другим
> пользователям: команды выполняются с правами администратора. Перед изменениями
> движок проверяет структуру каталогов и ставит `state\run.lock`, поэтому два
> экземпляра не могут одновременно перезаписать журнал. После аварийного закрытия
> lock-файл удаляйте только убедившись, что другой экземпляр не запущен.

Посмотреть, что будет сделано, ничего не меняя:

```bash
wintweaks.cmd apply /dry /profile:core
```

Применить:

```bash
wintweaks.cmd apply /profile:core /strict
```

Откатить всё обратно:

```bash
wintweaks.cmd revert
```

## Меню (основной способ работы)

Двойной клик по `menu.cmd` — или из консоли:

```bash
wintweaks.cmd menu
```

Меню — каталог: **каждый пункт выполняется отдельно**. При запуске и после
каждого действия оно сканирует ваш ПК и подстраивает список под то, что у вас
реально есть.

```
  Система : Windows 11 Pro 25H2 (сборка 26200.9168)
  Журнал  : применено 1, откачено 1, вручную 0
------------------------------------------------------------------
  Режим   : [ ] пробный прогон, ничего не менять   - клавиша D
            [ ] точка восстановления перед изменением - клавиша T
            [ ] показывать то, чего нет на этом ПК     - клавиша H
            [ ] глубокое удаление приложений со следами - клавиша G
------------------------------------------------------------------
    1. Приватность и телеметрия            готово 14 из 30
    2. Интерфейс и Проводник               готово 11 из 26
    3. Службы                              готово 0 из 77
    4. Задачи планировщика                 готово 0 из 5
    5. Обновления Windows                  готово 0 из 4
    6. Производительность и игры           готово 1 из 3
    7. Microsoft Edge                      готово 0 из 4
    8. Встроенные приложения               готово 0 из 14
    9. Система: питание, сеть, диск        готово 0 из 6
   10. Очистка диска                       готово 0 из 8
------------------------------------------------------------------
   S. Статус и журнал      V. Проверка системы     L. Логи
   P. Создать точку восстановления сейчас
   R. ОТКАТИТЬ ВСЁ         0. Выход
```

Внутри категории каждый пункт имеет состояние:

```
  [+] сделано нами   [=] уже в нужном состоянии   [ ] не выполнено
  [-] нет на этом ПК  [x] недоступно в этой версии Windows
```

Номер пункта открывает карточку: что именно меняется, что перестанет работать,
тип, риск, **есть ли откат** и текущее состояние объекта (например, нынешний тип
запуска службы). Кнопка «Откатить» показывается только там, где откат есть.

### Каталог подстраивается под ваш ПК

Перед показом меню запускается инвентаризация: `helpers.ps1 -Action Inventory`
читает `data	weaks.def` и для каждого пункта выясняет две вещи — существует ли
объект на этой машине и не находится ли он **уже** в нужном состоянии.
Результат кладётся в `state\inventory.dat` строками `ID|PRESENT|ALREADY|INFO`.

Что это даёт на практике: из 187 пунктов каталога на конкретной машине
показывается только то, что там есть. Например, приложений в каталоге 33, а в
меню видно 14 — остальные просто не установлены. Пункты, которые кто-то уже
настроил до нас, помечены `[=]` и не выполняются повторно.

Отсутствующие пункты по умолчанию скрыты; клавиша `H` показывает их со знаком
`[-]`, если вы хотите видеть каталог целиком.

### Точка восстановления — по вашему решению, а не автоматически

Раньше `apply` пытался создать точку восстановления при каждом запуске. Это было
неправильно, и теперь поведение такое:

| Ситуация | Что происходит |
|---|---|
| Меню, по умолчанию | Точка **не** создаётся, движок получает `/no-restore-point` |
| Клавиша `T` в меню | Точка создаётся перед каждым изменением |
| Пункт `P` в меню | Создать точку прямо сейчас, разово |
| CLI без ключей | Спрашивает один раз за запуск |
| CLI с `/restore-point` | Создаёт всегда |
| CLI с `/no-restore-point` | Не создаёт никогда |
| CLI с `/yes` | Не создаёт (иначе автоматизация зависла бы на вопросе) |

Точка восстановления для отката **не нужна** — каждый твик и так пишет
собственную резервную копию, и `revert` работает без неё. Это дополнительная
страховка на уровне всей системы. Учтите: Windows сама по себе не делает больше
одной точки в сутки, так что даже при включённом `T` она создастся не каждый раз.

### Почему в шапке было «Windows 10 Pro»

В реестре Windows 11 значение `ProductName` до сих пор равно **«Windows 10 Pro»** —
Microsoft не стала его менять ради совместимости со старым софтом, который
проверяет эту строку. Проверьте сами:

```bash
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion" /v ProductName
```

Определение версии в самом движке всегда шло по номеру сборки (`26200 >= 22000` →
Windows 11), и оно было верным. Сырое `ProductName` печаталось только в шапке
меню. Теперь имя системы собирается из номера сборки и `EditionID`, поэтому
показывается `Windows 11 Pro 25H2 (сборка 26200.9168)`.

## Встроенные приложения и Microsoft Edge

### Приложения: два режима удаления

**Обычный режим (по умолчанию).** `Remove-AppxPackage` без `-AllUsers` — снимается
только регистрация для вашей учётной записи. Файлы остаются в
`Program Files\WindowsApps`, в журнал пишутся `PackageFullName`,
`PackageFamilyName` и `InstallLocation`. Откат делает
`Add-AppxPackage -Register "<InstallLocation>\AppxManifest.xml"` — возврат
мгновенный, без Магазина и без интернета. **Проверено вживую на этой машине.**

**Глубокий режим (клавиша `G`, ключ `/deep`).** Дополнительно убираются следы:

| Что удаляется | Как возвращается |
|---|---|
| Регистрация пакета | `Add-AppxPackage -Register` |
| Данные приложения `%LOCALAPPDATA%\Packages\<Family>` | robocopy из резервной копии |
| Ключ активации `HKCU\...\ActivatableClasses\Package\<FullName>` | `reg import` экспортированной ветки |
| Provisioned-копия (заготовка для новых учётных записей) | **не возвращается** |

Порядок жёсткий: **сначала всё копируется, потом удаляется**. Payload снимается
через `robocopy /B` (режим архивирования — иначе `WindowsApps` не читается даже
администратором). Если копирование не удалось, удаление **не начинается вовсе**:

```
ABORTED APP-XXX [DEEP]: could not copy the payload - refusing to delete what we cannot restore
```

Резервная копия каждого приложения лежит в
`backups\<RUNID>ppx\<Имя пакета>\` — там `payload\`, `localdata\`,
`activatable.reg` и `meta.txt` с исходным путём установки.

**Честный предел глубокого режима.** Provisioned-запись — это копия, которую
Windows выдаёт каждой *новой* учётной записи. Восстановить её из локального
бэкапа нельзя: для этого нужен исходный `.msix`, которого на диске нет. Поэтому
после глубокого удаления и последующего отката приложение вернётся вам, но новые
учётные записи на этом ПК его уже не получат. В карточке это написано прямо:
`Откат: есть, кроме записи для новых учёток`.

Второй предел: Windows может отказаться регистрировать пакет из скопированной
папки (подпись пакета привязана к расположению). Откат сначала пробует исходный
путь установки, затем `RegisterByFamilyName`, и только потом нашу копию. Если не
вышло ни одним способом — данные и реестр всё равно восстановлены, а в логе будет
прямое указание переустановить приложение из Магазина.

27 пакетов в чёрном списке `data\protected.def` и не предлагаются никогда:
Магазин, установщик приложений, интерфейс Защитника (`SecHealthUI`), оболочка
(`ShellExperienceHost`, `StartMenuExperienceHost`), компоненты входа
(`AAD.BrokerPlugin`, `AccountsControl`, `LockApp`), панели NVIDIA и Realtek.

### Edge: сначала обратимое, удаление — отдельно

| Пункт | Что делает | Откат |
|---|---|---|
| `EDGE-STARTUP-BOOST` | Политика `StartupBoostEnabled=0` — Edge не висит в памяти после входа | полный |
| `EDGE-BACKGROUND-OFF` | Политика `BackgroundModeEnabled=0` — закрытый Edge выгружается | полный |
| `EDGE-NO-DESKTOP-ICON` | `CreateDesktopShortcutDefault=0` — обновления не возвращают ярлык | полный |
| `EDGE-TASK-CORE` / `EDGE-TASK-UA` | Отключают задачи автообновления Edge | полный |
| `EDGE-UNINSTALL` | Штатный `setup.exe --uninstall --system-level --force-uninstall` | **нет** |

`EDGE-UNINSTALL` честно помечен как необратимый: локальной копии Edge не
существует, поэтому «откат» может только напечатать команду переустановки.
В журнале такая запись получает статус `MANUAL`, и `status` показывает её
отдельно — чтобы вы видели, что там нужны руки. Вне ЕС Microsoft часто
блокирует удаление: тогда деинсталлятор вернёт ненулевой код, а Edge останется
на месте — это ожидаемое поведение, а не сбой скрипта.

**Что мы не трогаем:** `MicrosoftEdgeWebView2` — от него зависят Office, Teams,
виджеты и множество сторонних программ.

## Команды

| Команда | Что делает |
|---|---|
| `apply` | Применяет твики из `data\tweaks.def` согласно профилю |
| `revert` | Восстанавливает всё, что записано в `state\applied.dat` (в обратном порядке) |
| `status` | Показывает ОС и текущее состояние: что применено, откачено, зависло |
| `verify` | Только чтение: сравнивает живую систему с журналом |
| `cleanup` | Безопасная очистка диска (её `revert` не касается — см. ниже) |
| `system-change` | Обратимые изменения конфигурации: питание, сеть, файловая система |
| `menu` | Интерактивное меню на русском |
| `help` | Справка |

`verify` проверяет активные записи `REG`, `SVC`, `TASK`, `APPX`/`APPXDEEP`,
гибернацию, TCP autotuning, NTFS last access и три AC-тайм-аута схемы питания.
`MATCH` — совпадение, `DRIFT` — расхождение (включая отсутствие ожидаемого объекта),
`ERROR` — ошибка чтения, `UNSUPPORTED` — проверка такой записи не поддерживается.
Для реестра сравниваются и тип, и значение, включая пустую строку и DWORD
`0xffffffff`; используется путь из журнала, в том числе `HKU\<SID>`.
Изменённая цель в каталоге, отсутствующий ID, неподдерживаемый тип записи,
ошибка чтения и статусы `PENDING`/`FAILED`/`MANUAL` не считаются успехом.
Записи `REVERTED` пропускаются. Фильтры `/id:` и `/run:` ограничивают проверку.
Код возврата — `4`, если есть расхождения или непроверенные записи; иначе `0`.
Журнал хранит исходное состояние, поэтому целевое значение берётся из текущей
версии каталога, а не из исторической версии на момент применения.
Проверка AppX относится к текущей учётной записи. Для глубокого удаления также
проверяется отсутствие пользовательских данных, ключа активации и provisioned-копии.
Настройки питания читаются через штатный
[Win32_PowerSettingDataIndex](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/powerwmiprov/win32-powersettingdataindex).

## Профили и поштучный режим

Профиль нужен только для пакетного применения из командной строки. **В меню он
не используется** — там каждый пункт выполняется отдельно.

| Профиль | Твиков на Win11 | Состав |
|---|---|---|
| `core` | 22 | Только HKCU/UI и базовая приватность |
| `balanced` | 46 | + политики телеметрии, задачи CEIP, `DiagTrack`, виджеты, Delivery Optimization |
| `extended` | 59 | + Bing/Cortana в поиске, Xbox/Maps/Fax, отсрочка feature-обновлений |
| `extended /include-risky` | 62 | + `SysMain`, `WSearch`, Windows Error Reporting |
| `manual` | 124 | **Никогда не применяется пакетно.** Только по явному `/id:` |

Профиль `manual` — это каталог меню: приложения, Edge, оформление и прочие
пункты, которые имеют смысл только по одному. Явный `/id:` обходит проверку
профиля, поэтому такой пункт выполняется, даже если он не входит ни в один
пакет:

```bash
wintweaks.cmd apply /yes /id:APP-XBOX /id:UI-DARK-APPS
```

Откат — тем же способом:

```bash
wintweaks.cmd revert /yes /id:APP-XBOX
```

Отдельные шаги `system-change` и `cleanup` тоже адресуются через `/id:`:

```bash
wintweaks.cmd system-change /yes /id:SYS-LONGPATHS
```

## Как устроен откат «в точности прежнее состояние»

Мы не откатываем «твик» — мы восстанавливаем **ровно те примитивы, которые тронули**.
Исходное состояние снимается *до* изменения и хранится не как дельта, а как полное
описание прежнего значения.

| Объект | Модель прежнего состояния | Точность |
|---|---|---|
| Значение реестра | Тройка `(STATE, TYPE, DATA)`, где `STATE ∈ {ABSENT, PRESENT}`. «Значения не было» и «значение было равно 0» — это **разные** состояния | Точная. Не восстанавливаются только ACL и timestamp ключа — мы их не меняем |
| Ключ реестра целиком | `reg export` ветки в `.reg` — страховочная копия | Вторичный механизм: `reg import` не удаляет добавленное, поэтому автоматически не используется |
| Служба | `(StartMode, State, DelayedAutoStart)` из CIM (`Win32_Service`), а не из локализованного вывода `sc qc` | Точная для типа запуска и факта «была запущена» |
| Политика | Это тот же реестр → та же тройка | Точная на не-доменной машине. На доменной GPO может перезаписать — есть предупреждение |
| Задача планировщика | `State` из `Get-ScheduledTask` + XML-экспорт задачи как страховка | Точная для флага enable/disable — только его мы и меняем |
| Схема электропитания | `powercfg /export` в `.pow` + GUID активной схемы из реестра | Точная: импорт возвращает все параметры схемы |
| Гибернация / Fast Startup | Значения `HibernateEnabled` / `HiberbootEnabled` до изменения | Точная |
| TCP autotuning | Текущее значение из `Get-NetTCPSetting` | Точная |
| Команды DISM/cleanmgr | Необратимы по природе | **Не откатываются** — вынесены в `cleanup`, из `apply`/`revert` исключены |

### Если ключ создали мы

Поле 9 журнала хранит не флаг, а **путь самого верхнего ключа, которого до нас не
существовало**. Пример: твик `UI-CLASSIC-CONTEXT` пишет в
`…\Classes\CLSID\{86ca1aa0-…}\InprocServer32`; `CLSID` уже есть, а `{86ca1aa0-…}`
нет — значит в журнал попадает `…\CLSID\{86ca1aa0-…}`, и откат удаляет именно эту
записанное значение и только пустые созданные ключи. Позднее добавленные чужие значения и подразделы сохраняются.

### Три правила, обеспечивающие безопасность повторов

1. **Write-ahead.** Запись в журнал делается *до* мутации, со статусом `PENDING`;
   после успеха статус переписывается в `OK`. Если процесс убили посередине —
   `status` покажет `[PENDING!]`, а `revert` корректно обработает такую строку
   (для write-ahead записи откат безопасен, даже если мутация не произошла).
2. **История изменений.** Каждое фактическое изменение сохраняет состояние перед
   ним в записи текущего запуска. Это относится и к повторному применению после
   внешнего изменения, и к одинаковому ID для разных SID. Старые записи остаются
   неизменными; полный откат проходит всю историю от новых записей к старым.
3. **Идемпотентность.** Перед изменением текущее значение сравнивается с целевым;
   равны — `SKIPPED-SAME`, в журнал ничего не пишется. Повторный `revert` находит
   только `REVERTED` и завершается с кодом 0.

Выборочный откат не разрешает перезаписать более новое неоткаченное изменение
того же объекта или удалить его родительский ключ. Сначала откатите новый запуск.
Если восстановление не удалось, обход останавливается: старые снимки не должны
перекрывать ещё не восстановленный новый. Запись остаётся доступной для повтора.

### Транзакционность

С ключом `/strict` первая же ошибка приводит к автоматическому откату **всех**
шагов текущего `RUNID` в обратном порядке и выходу с кодом 4. Без `/strict` работа
продолжается, ошибки считаются, а в конце выводится точная команда для отката
конкретного запуска: `wintweaks.cmd revert /run:<RUNID>`.

При ошибке записи самого журнала применение останавливается с кодом `4`, включая
режим `/strict`. Автоматический откат в этом случае не запускается: сначала нужно
восстановить возможность записи и проверить сохранённые записи через `status`.

## Guardrails

Проверяются до любого изменения:

1. **Права администратора** (`fltmc`) — иначе код 2.
2. **Версия ОС**: `CurrentBuild ≥ 17763` (Win10 1809) и `InstallationType=Client` — иначе код 3.
   Семейство определяется по билду: `≥ 22000` → `win11`, иначе `win10`; твики с
   `OS=win11`/`OS=win10` на чужом семействе дают `SKIPPED-OS`.
3. **DENYLIST** (`data\protected.def`) — 52 записи: ядро RPC/WMI/журналов, профили и
   криптография, **вся защита Windows** (`WinDefend`, `MpsSvc`, `SecurityHealthService`,
   `wscsvc`, `BFE`, `Sense`), обслуживание (`TrustedInstaller`, `wuauserv`, `UsoSvc`,
   `AppXSvc`), сетевая база (`Dhcp`, `Dnscache`, `NlaSvc`), а также ключи `Winlogon`,
   `SafeBoot`, `Memory Management`, `BCD00000000`, `SAM`, `SECURITY`.
   Любая попытка тронуть их останавливает работу с кодом 6.
4. **Доменная машина** — предупреждение и отдельное подтверждение: GPO может
   перезаписать политики обратно после отката.
5. **Контекст HKCU** — в лог пишется SID пользователя, чей куст будет изменён.
   Если скрипт запущен из-под другой учётки, используйте `/user-sid:<SID>`.
6. **Ситуативные guard'ы**: `SysMain` отключается только если системный диск —
   SSD/NVMe; `XboxGipSvc` пропускается при подключённом геймпаде; `powercfg /h off`
   пропускается на ноутбуках (обнаружена батарея).

## Что мы принципиально не делаем

| Не делаем | Почему |
|---|---|
| Не трогаем Windows Defender ни в каком виде | Прямое требование безопасности; в DENYLIST |
| Не удаляем защищённые AppX-пакеты и компоненты Windows | Они нужны системе; исключены списком `protected.def` |
| Не подменяем оболочку, не правим `bcdedit`/загрузку | Классические причины чёрного экрана и незагружаемой системы |
| Не отключаем обновления (`wuauserv`, `NoAutoUpdate`) | Только отсрочка **функциональных** обновлений через штатную политику WUfB |
| Не запускаем `DISM /ResetBase`, не удаляем `Windows.old`, не включаем «Очистку обновлений» | Необратимо лишает возможности откатить обновления |
| Не трогаем pagefile, TRIM, `netsh winsock reset`, DNS | Либо рискованно, либо откат неточен |
| Не трогаем бинарную маску `UserPreferencesMask` | Высокий риск ошибки при частичном восстановлении; заменено точечными значениями |

## Очистка диска (`cleanup`)

Удаление временных файлов необратимо по природе, поэтому **ничего из `cleanup` не
пишется в журнал и `revert` этого не касается**. Каждый необратимый шаг спрашивает
подтверждение отдельно и поддерживает `/dry` (показывает объём, ничего не удаляя).

| Шаг | Что делает |
|---|---|
| `CLN-USERTEMP` / `CLN-WINTEMP` | Файлы старше 3 дней в `%TEMP%` и `%SystemRoot%\Temp`; занятые пропускаются |
| `CLN-CRASHDUMPS` | `%LOCALAPPDATA%\CrashDumps` старше 7 дней |
| `CLN-DO-CACHE` | `Delete-DeliveryOptimizationCache` |
| `CLN-WU-DOWNLOAD` | Только `SoftwareDistribution\Download`. `DataStore` (журнал обновлений и возможность их удалить) не трогается |
| `CLN-CLEANMGR` | `cleanmgr /sagerun:64` с белым списком обработчиков: Temporary Files, Thumbnail Cache, Delivery Optimization Files, Windows Error Reporting, Downloaded Program Files. Windows.old, Update Cleanup, корзина и Downloads принудительно выключены. Ветка `VolumeCaches` перед этим экспортируется в бэкап |
| `CLN-DISM` | `StartComponentCleanup` **без** `/ResetBase` |
| `CLN-RECYCLE` | Только с `/include-recycle` и отдельным подтверждением — это пользовательские данные |

В конце выводится свободное место на системном диске до и после.

## `system-change` — обратимые изменения конфигурации

Всё журналируется как обычный твик, поэтому `revert` откатывает и это.

| ID | Изменение | Откат |
|---|---|---|
| `SYS-POWER-SCHEME` | Тайм-ауты активной схемы (AC): монитор 20 мин, сон и диск выключены | `powercfg /import` сохранённого `.pow` + `/setactive` — побайтовое восстановление схемы |
| `SYS-HIBERNATE-OFF` | `powercfg /h off`, освобождает `hiberfil.sys`. На ноутбуках пропускается | `powercfg /h on` |
| `SYS-FASTSTARTUP-OFF` | `HiberbootEnabled=0` — обычное выключение вместо гибридного | Восстановление значения из журнала |
| `SYS-LONGPATHS` | `LongPathsEnabled=1` — пути длиннее 260 символов | Восстановление значения из журнала |
| `SYS-TCP-AUTOTUNING` | `autotuninglevel=normal` (значение Windows по умолчанию) | `netsh int tcp set global autotuninglevel=<прежнее>` |
| `SYS-LASTACCESS` | NTFS перестаёт обновлять время последнего доступа | `fsutil behavior set disablelastaccess <прежнее>` |

Если экспорт схемы питания не удался — твик **пропускается**: мы не меняем то,
что не смогли забэкапить.

### Два инженерных решения, о которых стоит знать

**Кодировки.** Все `.cmd` и `.def` — строго ASCII, описания в них на английском.
Консоль CMD работает в OEM-кодировке, а `chcp 65001` в batch ломает разбор `for /f`
и перенаправления. Вся русская документация живёт здесь, в `README.md` (UTF-8).

**Локализация системных утилит.** Вывод `sc qc`, `schtasks /query`,
`powercfg /getactivescheme` и `netsh int tcp show global` переводится на язык
системы, и разбор по номеру токена ломается на русской Windows. Поэтому:
*изменения* делают нативные утилиты (`reg`, `sc`, `schtasks`, `powercfg`), а
*состояние снимается* через `helpers.ps1`, который печатает стабильные ASCII-строки
`KEY=VALUE`. Реестр читается через Registry API, включая значение по умолчанию. Если исходный тип или строку нельзя безопасно сохранить в CMD-журнале, изменение останавливается до записи.
Активная схема питания читается из реестра (`ActivePowerScheme`), а не из вывода
`powercfg`. `wmic.exe` не используется вообще: в сборках 26xxx это отключаемый
компонент, которого может не быть.

### Формат журнала `state\applied.dat`

```
RUNID|ID|TYPE|TARGET|NAME|PREV_STATE|PREV_TYPE|PREV_DATA|KEY_CREATED|RESULT|TIMESTAMP
```

Пример реальных записей:

```
20260829_024258|UI-FILEEXT|REG|HKCU\...\Explorer\Advanced|HideFileExt|PRESENT|REG_DWORD|0x1|0|OK|...
20260829_024258|PRIV-TELEMETRY|REG|HKLM\SOFTWARE\Policies\...\DataCollection|AllowTelemetry|ABSENT|-|-|HKLM\SOFTWARE\Policies\Microsoft\Windows\DataCollection|OK|...
20260829_024258|PRIV-SVC-DIAGTRACK|SVC|DiagTrack|-|PRESENT|Auto|Running|0|OK|...
```

Ограничения формата: в полях не
должно быть пустых значений (используйте `-`), символа `|` и восклицательного знака.

Движок проверяет структуру журнала перед работой. Ошибка добавления записи
останавливает соответствующее изменение. Обновление статуса выполняется через
временный файл в том же каталоге и атомарную замену: при ошибке замены исходный
журнал сохраняется, команда завершается с кодом `4`. Кодировка сохранённых полей
при обновлении статуса не меняется. Повреждённый журнал автоматически не чинится.

## План проверки

Автоматические проверки без изменения системных настроек:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests\runtime.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests\failures.ps1
```

Они проверяют валидацию данных, владение блокировкой, сохранность журнала при
ошибке записи, вызовы из CMD, `/dry`, фильтры и обнаружение расхождений в `verify`.
Системные запросы в тестах `verify` подменены контролируемыми ответами; полный
цикл применения и отката по-прежнему требует тестовой ВМ.
Тесты отказов подменяют системные команды временными исполняемыми файлами;
реестр, службы, приложения и параметры рабочей Windows не изменяются.

### 1. Среда

Первый прогон — **только на тестовой ВМ с чекпоинтом**. Матрица: Win11 (целевая),
Win10 22H2, Win11 Home (проверка `SKIPPED-EDITION`/поведения политик). На боевой
машине — после прохождения цикла на ВМ.

### 2. Снимок «до»

```bash
reg export "HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced" before_adv.reg /y
```

Плюс состояние служб и задач:

```bash
schtasks /Query /FO CSV > before_tasks.csv
```

### 3. Прогон

1. `apply /dry /profile:extended` — в системе не должно измениться ничего;
   `state\applied.dat` остаётся пустым, в логе только строки `DRY`.
2. `apply /profile:extended /strict` — применение.
3. **Перезагрузка** и чек-лист живучести:
   - система грузится, появляется экран входа;
   - рабочий стол и панель задач отрисованы, меню «Пуск» открывается;
   - Проводник открывается, контекстное меню работает, `Win+E` и `Win+R` → `notepad`;
   - `sfc /verifyonly` не находит нарушений целостности;
   - запущены `RpcSs`, `Winmgmt`, `EventLog`, `Schedule`, `WinDefend`, `MpsSvc`, `Dnscache`;
   - в «Безопасности Windows» защита в реальном времени **включена**;
   - «Проверить наличие обновлений» отрабатывает без ошибки;
   - `Test-NetConnection www.microsoft.com -Port 443` успешен.
4. **Идемпотентность**: повторный `apply` даёт только `SKIPPED-SAME` /
   `REAPPLY`, число строк в журнале не растёт.
5. `verify` — сверка живого состояния с журналом, без изменений.
6. `revert /dry` — печатает точный обратный план.
7. `revert` — затем сравнение со снимком «до»:

```bash
fc /u before_adv.reg after_adv.reg
```

   **Критерий приёмки: экспорт реестра, состояние служб и задач после `revert`
   совпадают со снимком «до `apply`».**
8. Повторный `revert` → «нечего откатывать», код 0.

### 4. Тест частичного сбоя

Добавить в `tweaks.def` заведомо невалидную строку (несуществующий тип значения) и
запустить `apply /strict`: ожидается ошибка на этой строке, автоматический откат
всех уже применённых записей текущего `RUNID` в обратном порядке и код 4.
Прерывание `Ctrl+C` посередине оставляет запись `PENDING` — `status` её показывает,
`revert` корректно обрабатывает.

### 5. Контроль принципа наименьших привилегий

Запустить `apply` под Process Monitor с фильтром `Operation = RegSetValue` и
сверить список фактически изменённых значений со списком ID в журнале.
**Ни одного значения вне журнала быть не должно.**

### 6. Проверка `cleanup`

`cleanup /dry` не меняет свободное место. После реального `cleanup`:
`sfc /verifyonly` чист, `DISM /Online /Cleanup-Image /CheckHealth` сообщает об
отсутствии повреждений хранилища компонентов, журнал обновлений на месте, удаление
последнего обновления по-прежнему доступно.

## Аварийное восстановление вручную

Если по какой-то причине `revert` недоступен, в `backups\<RUNID>\` лежат:

- `*.reg` — экспорты изменённых веток (импорт: двойной клик или `reg import файл.reg`);
- `svc_*.reg` — ветки служб `HKLM\SYSTEM\CurrentControlSet\Services\<имя>`;
- `task_*.xml` — определения задач планировщика;
- `scheme_<GUID>.pow` — схема электропитания (`powercfg /import файл.pow <GUID>`);
- `volumecaches.reg` — настройки обработчиков «Очистки диска».

Плюс точка восстановления системы, которую `apply` пытается создать перед работой
(если защита системы включена).

### Автоматические проверки

GitHub Actions проверяет каталог, журнал и обработку отказов на Windows Server 2022 и 2025.
Интеграционные проверки создают временные ключи реестра, службу и задачу только на
одноразовых GitHub-hosted runners и проверяют применение, verify и откат.
Это не заменяет полный цикл на клиентской Windows с перезагрузкой.
